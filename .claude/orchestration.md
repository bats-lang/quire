# Orchestration: the standing rules of the session that runs the workers

This file is for the orchestrator (the session that spawns workers, reviews and merges), not for the workers: it is not under `.claude/rules/` or `.claude/skills/`, so nothing loads it by itself. The orchestrator rereads it at the start of every session and after every compaction. The owner's words are the authority; when a rule here and the owner's last word differ, the owner's last word wins and this file is changed the same day. A marker `(owner, <timestamp>)` carries the owner's words verbatim, in quotation marks, and the timestamp of the message that holds them (`2026-10-21T10:36:06Z`, not a date); nothing paraphrased is marked as the owner's. A rule the orchestrator drew from the owner's words, or from a mistake, is marked `(orchestrator, <date>)` and stays no stronger than that. The owner's words are never extended: a rule written wider than what the owner said (`no sed`, `no redirect to /dev/null`) is a mistake of this file, found by `tests/static/guidelines.py`.

## Priorities

The priorities (p0 to p3), the order of work, the owner's rule on downgrades and the Android-release hold are defined once, in quire's `CLAUDE.md`, section "Priorities". This file does not restate them. The orchestrator works tickets in that order.

## Agents and slots

The hourly slot check runs this section, and nothing in it needs another section: run `ListAgents`, fill each free slot in the order of step 2, and do nothing only when `ListAgents` shows two live agents.

1. **Run `ListAgents` first.** It is the only truth about what runs: run it before any statement about what is running, which slot is free, or whether a worker is alive. The `slots` ledger is kept by hand, goes stale (a dead agent still shows in it) and is never an answer: it is a note to correlate with `ListAgents`. "All slots are full" is said only after `ListAgents` shows two live agents.
2. **A free slot is filled the same turn, in this order**, oldest first inside each step (`qsweep`'s `NEXT FOR A FREE SLOT` line orders each category by the PR's creation date, oldest first, across quire and every library repository). The owner's words (owner, 2026-10-20T04:16:40Z): "priorities are:", then "Fix for a review that asked for changes", "Review for a fix that's ready", "A new PR", and "As always inside each category, go by oldest." The owner's words (owner, 2026-10-21T03:18:18Z) on who takes a fix: "it doesn't have to be "the same". It just has to be an author". The red CI and the merge conflict in step (1), and step (3) as CLAUDE.md's order, are the orchestrator's reading of the owner's rules (the merge-conflict bullet below).
   * (1) a fix, by an author (any author, not necessarily the one who wrote the PR), for a review that asked for changes, a red CI, or a merge conflict (a conflict is fixed as a red CI is: merge main in, resolve, check, push);
   * (2) a review of a PR green on its exact head (every required check finished and green: `qsweep` prints `READY-FOR-REVIEW`), by an agent that is not its author;
   * (3) the oldest ticket of the highest priority (CLAUDE.md, Priorities).

   Never a new ticket while a changes-needed review, a red CI or a merge conflict waits for its fix, or a green PR waits for its reviewer. `qsweep` prints step (1) as `NEXT FOR A FREE SLOT`.
   * **The order of work, as the owner ruled it on 2026-10-28** (orchestrator, 2026-10-28, the owner's ruling of that date): open pull requests come first, oldest first: fix a red CI, address a review that asked for changes, review a green PR, merge a PR that is reviewed approved and green. Only then the tickets, by priority, and within a priority by age.
3. **A reviewer starts only when every required check is finished and green on the exact head.** A PR whose CI is still running is not reviewed, and a review of a PR in progress is never started to fill a slot.
4. **At most two agents run at any time, reviewers included** (orchestrator, 2026-10-18, from the owner's slot count). The owner's words (owner, 2026-10-17T20:07:29Z): "go down to one sonnet, one haiku until I say otherwise", and (owner, 2026-10-18T04:35:18Z): "Please fix slots to also warn about too many agents". That a review takes a slot like any work, and "never a third agent beside two busy slots", are the orchestrator's reading of them. Slots now: one sonnet and one haiku; it changes only when the owner says.
   * **The cap is a target** (orchestrator, 2026-10-28, the owner's ruling of that date): the session starts with two sonnet slots, reviews count in them, and the number of agents is never over the cap and never under it. The number itself is the owner's to change.
5. **A slot is never held idle** (owner, 2026-10-19T02:00:17Z: "Never, under any circumstances, is an empty slot acceptable. This is a hard rule"). Not for a fix that is coming, not for a better fit. "Nothing fits" is not an answer: break a ticket up, take a conflicted PR, or take the next ticket of CLAUDE.md's order (a p1 is not started while a p0 is open, whether or not a worker has the p0 in hand). Record the spawn with `slots set` after calling Agent (setting the ledger starts nothing).
6. **An interrupt that killed agents is not a stop** (owner, 2026-10-21T04:29:23Z): "Yes. Unless I explicitly say "quiesce agent", assume I still want agents running, just doing the right thing." Unless the owner says "quiesce agent", agents stay running: a killed one is restarted fresh, with the corrected method, in the same turn. Nobody waits for a "go" (the orchestrator's reading).
   * **An agent is stopped only when the owner asks, or for a huge issue** (orchestrator, 2026-10-28, the owner's ruling of that date). Nothing else stops an agent: not pressure, not a slow run, not a guess.
7. **No predictive scheduling; evidence is produced, not awaited** (owner, 2026-10-20T13:51:18Z: "This whole predictive scheduling shit has been inverting priorities for too long"; owner, 2026-10-20T22:06:51Z: "We don't hunt. We don't wait."; owner, 2026-10-21T03:45:57Z: "Dependencies are fine, because they are actionable."). A ticket is never skipped, reordered or held for what an open PR will do, for a guessed blocker, or until evidence turns up: producing the evidence (pushing the PR, running the hunt) is the work. Dependencies are fine: the dependency is its own ticket and PR, worked first. A step that waits for time or a recurrence is done now; no wake-up is scheduled for it. The only ticket skipped is one that needs a human step an agent physically cannot do, marked openly. (The sentences that follow the quotes are the orchestrator's wording of them.)
8. Every agent, haiku included, takes the highest-priority, oldest ticket it can fix. A haiku takes the oldest p0 when unsure; it is never asked whether it can. Judge by the outcome: a diff that is totally off, or a worker that stops midway, is enough to decide it cannot; then the ticket goes to a sonnet and the haiku takes the next p0. A ticket is never skipped or reordered for a guessed conflict with an open PR: conflicts are resolved at merge time.
9. Reviewers are separate agents from the author, one at a time, briefed with the repository's own rules, the issue's goal and the kind of change. No invented threat models. Never say "human review".
10. The ledger is the `slots` command (`slots`, `slots set SLOT AGENT TASK`, `slots free SLOT`); `qsweep` ends with it. The hourly check fills the free slots in the order of step 2 in the same turn.

## Merge conflicts

* **A PR with a merge conflict is next in line for work** (owner, 2026-10-18T20:05:02Z: "If an open PR has conflicts, that counts as "PR in progress" for our rules that PRs in progress trump everything. It shouldn't stop a worker, but it should be next in line for work (and most conflicts are probably haiku-level)."). That it is an author's fix, in the free-slot order of "Agents and slots" (step 1, with a red CI), is the orchestrator's reading: it does not stop a worker that is running, but it is next in line for the next free slot.
* Most conflicts are haiku-level: merge main in, resolve, regenerate lockfiles or `bootstrap/c` with the repository's own tooling, check, push. Merge, never rebase or force-push. A conflict where both sides changed the same logic goes to a sonnet.
* Every sweep lists the open PRs whose mergeable state is dirty or conflicting.

## Tickets

* **A ticket that should be several is broken up BEFORE work starts** (owner, 2026-10-18T20:19:33Z: "close the "umbrella" ticket as "broken into <components>". This should be a standing rule"). An agent that finds a ticket holding more than one piece of work files one ticket per piece, taken from the steps already in the ticket (not new scope), closes the original with a comment "Broken into #a, #b, #c", and then works the pieces in the order planned, each in a PR of its own (one ticket, one PR; a brief never asks for a dependency's piece in the same PR). A piece that depends on another says so in its body ("This ticket cannot be worked on until #n is resolved"). The new tickets inherit the priority and labels of the ticket they break. An umbrella whose pieces all exist as tickets is closed the same way. Every worker brief carries this rule.
* **A flake ticket is closed only when the work was already done** (owner, 2026-10-18T20:35:29Z: "The only reason we closed *these* with a comment is because WE ALREADY DID THE WORK"): the cause found and fixed, or the instruments and analysis built so the next failure arrives with data. Never closed in place of work. With no known cause, root-cause it first with the instruments built for it (stall capture, gdb on crashes and hangs, diagnostics, a lab loop); where the capture is not enough, the ticket's action is "add the data capture". With a known cause, fix it. A ticket whose only content is `wait and see` is closed at once; no "watch" ticket stands in for work. If a closure was a misreading, reopen it with the actionable item.

## Briefs and the machine

* A brief names the ticket, the files and docs to read, the repository's own rules, the kind of change, the check before pushing, and the rules above that apply. It copies the ticket's Done-when word for word and adds nothing to it, takes nothing from it (the brief neither narrows it nor tells the worker to measure less or more than it says), and offers no alternative to it: nothing like `or say what is true`, `or remove the claim`, `honest` or `frank`, which always mean narrowing. Before the Agent call, run `python3 tests/static/guidelines.py --brief <brief> --ticket <ticket body>` (the ticket body: `gh api repos/bats-lang/quire/issues/N --jq .body`); a finding is fixed before the brief is sent.
* Every worker brief says: the worker.md rules; finish inside the turn; do not merge; do not write the review. Every reviewer brief says: the reviewer.md rules, and that a reviewer runs nothing. A reviewer brief is sent only when `qsweep` prints `READY-FOR-REVIEW` for the PR, and names the head SHA.
* **A brief for a change to a published signature carries the line** `Overlap: the old form stays beside the new one, with a deprecation comment (area keyword and removal ticket) and a test that calls it; one published version holds both; the p2 removal ticket is filed with the change (CLAUDE.md, "Breaking changes keep at least one published version of overlap").` **A reviewer brief for it carries that line and this one** `Overlap check: the old form is still there beside the new one; a test calls it; it has a deprecation comment naming the area by keyword and the removal ticket; the removal ticket exists, is p2, and is cited in the deprecation comment; a signature changed in place is Verdict: changes needed.` The lint refuses a brief that names a change to a published signature and lacks the matching line (`guidelines.py --brief`), and a review of one that lacks the check (`--review`).
* **A worker brief carries four lines**, each beginning with its label, and `guidelines.py --brief` refuses a brief that names `worker.md` and lacks one:
  * `Design check: push the ticket's declarations (types and statements, no proofs or bodies) to the branch before building on them and hand back with DESIGN CHECK; a reviewer reads only those against the ticket and the repository's types and approves or sends back; then build.`
  * `Push: push the ticket's branch after every commit (a branch push opens no pull request and starts no CI), so the work survives the container and a reviewer can read it.`
  * `Expects: write reject expects with bats fixtures --bless (bats#522) after the last edit of a module, never by hand or by repeated population runs; until bats#522 merges, from the observed error of one run of each changed snippet.`
  * `Sample: a local run over a population is a seeded sample (CLAUDE.md, "Check locally before every push"); CI runs the whole population.`
  A reviewer reads a design check as the brief for it says: only the declarations, against the ticket and the repository's types.
* Every hand-back is read against worker.md's form (PR, head, one evidence link per Done-when item); one with narration, hedging or a flagged "slip" that is no rule is sent back. `python3 tests/static/guidelines.py --text <hand-back>` finds the phrases.
* **"This machine lacks X" is never an excuse** (owner, 2026-10-18T22:16:41Z: ""This machine lacks" is never an excuse unless physically impossible to fix."), unless fixing it is physically impossible. If CI has a tool, package, browser, voice, font or setting a test needs, the worker installs it on its machine (apt as root, a scratch HOME for per-user things), runs the real thing, and documents the setup in quire's "Check locally" section. A report that says "did not run: the machine lacks" is sent back.
* **`/dev` is not written to by a worker** (owner, 2026-10-21T01:35:13Z: "I agree workers shouldn't *trash* /dev/null, but that's different from redirection"). The rule is: do not create, move, link, delete or truncate anything under `/dev`. Redirecting output to `/dev/null` is fine. A brief says so. (The ban on redirecting, written in 2026-10-18 after two workers damaged `/dev/null`, was the orchestrator's and is withdrawn.)
* **Checked-in code and YAML do not depend on sed** (owner, 2026-10-19T00:08:48Z: "please don't depend on `sed` being available on the machine"). Nothing more: a worker edits with any tool.
* **Disk is a shared allowance** (owner, 2026-10-20T04:34:45Z: "if there's disk pressure, I expect you to look for stragglers"). Under pressure `qsweep` lists the stragglers, the work that exists only on this machine.
* **Checkouts persist** (orchestrator, 2026-10-21). A worker keeps its checkout and its `build/` between tickets (a new branch in the same checkout), so its checks are incremental; a fresh clone deleted afterwards makes every `bats check` cold (10 to 15 minutes). Keep the shared browsers directory and the GMP ATS2 install.

## Pushing and merging

* Before any push or merge: `qsweep pressure` (prints one line, exits 0 only on `runner pressure: none`); `qsweep push <git push arguments>` is that check and the push in one command, and workers push with it. Under pressure, hold; do not push.
* **A worker never waits for CI checks** (quire#708 comment 3, 2026-10-20T04:22:42Z, the owner's standing rule as recorded on the ticket by the orchestrator: "a worker never waits for CI checks. It pushes, then hands back at once with the PR number, the exact head sha and what it ran locally; the orchestrator watches the checks and continues the process (review when green on the exact head, fix when red, merge)."). A worker brief says so, and the orchestrator is the one that watches the checks.
* At most 2 merge-queue entries. Cancel superseded runs (the queue's `supersede.yml` does it). No stacked PRs. No hooks. Many small PRs (repins) go in batches of about six with a pressure check before each; avoid bursts: CI capacity is the constraint.
* **Quire CI-triggering actions are 15 minutes apart** (orchestrator, 2026-10-28, the owner's ruling of that date). A push to a non-draft quire PR and a merge into quire's main are each at least 15 minutes after the previous one, and each is held while `qsweep pressure` reports pressure.
* **bats PRs that touch `src/` are serialized** (orchestrator, 2026-10-28, the owner's ruling of that date): exactly one is in flight in bats-lang/bats, no more and no less. When it merges, the next is already in hand.
* A PR merges only after an independent review comment for its head. Gated repositories (bridge, pwa, capacitor-plugins) need the exact form their CLAUDE.md gives; a push, an update-branch or a merge of main voids an approval. Use merge, not squash. quire merges through the queue (`enable_pr_auto_merge` MERGE); the others by `merge_pull_request`.
* A PR that adopts new package versions runs `bats lock --repository <dir>` and commits `bats.lock`.

## Checkouts

The checkouts the agents load (`/home/user/<repo>` for each repository: quire, bats, pwa, bridge, dom, gestures, arith, array, zip, sha256, capacitor-plugins, repository-prototype; the 14 files an agent loads are those 12 repositories' CLAUDE.md and the `.claude/rules/bats.md` of bats and of dom) stay on `main` with a clean tree, so the CLAUDE.md an agent reads is the merged one (quire#732). Nothing is left on a feature branch there, and no worker works in one (a worker has a worktree of its own beside it, worker.md, so the user-level stop hook, which reads the orchestrator's directory, has nothing to complain about; `qsweep` prints `STRAY-WORK` for one that is off main or not clean): a checkout with unpushed commits pushes them to their own branch first, and a checkout with uncommitted work has it committed or moved aside before it moves. The orchestrator fast-forwards each one to main (`git fetch origin main && git checkout main && git merge --ff-only origin/main`) at the start of every session and after every compaction.

## The orchestrator's own working rules (not the owner's)

* Nobody deletes the persistent checkout (CLAUDE.md, "Check locally"): the worktree a worker reuses for its next ticket, the one whose pull request merged last, and the orchestrator's own `/home/user/<repo>`. Only when the disk is at 90 percent does `qsweep clean` remove another worktree, and only one whose pull request is merged and whose tip is in `origin/main`; a worktree of a ticket in flight is never removed, and otherwise `qsweep` reports it as reusable. The number is the orchestrator's.
* `.claude/skills/sweep/` holds `qsweep` and `slots` (quire#751): stopgaps until they move into bats (bats-lang/bats#435). quire#573 (p3) keeps them in the repository as a skill; the Python package its comments name (pitboss, in dev-skill-up/pitboss) is not bats and is not that move.

Nothing here depends on a file under `~/.claude`: no hook is to be set up. The owner wrote (owner, 2026-10-21T10:36:06Z): "I'm not going to install stop hooks manually each session. That is insane." The same message begins with a sentence the orchestrator had written at 2026-10-21T10:34:24Z, which the owner sent back; that sentence is the orchestrator's and is not quoted here. ## Published APIs

* **API changes are additive** (owner, 2026-10-19T03:25:55Z: "keep the old signatures and add the new ones beside them. <-- Yes, that would have been the right decision. Please fix things to choose this path"). A change to a published package's API keeps the old signatures and adds the new ones beside them, named in words. Dependents move one at a time, in PRs of their own, under their normal CI; removal of the old form is a separate ticket once every dependent has moved. No lockstep publish, and no archive built outside a dependent's CI. Reason: process#62 replaced `spawn*`, pwa's published archive then failed repository-prototype `verify` in #359, and the fix was process#65, which is additive.
* **Breaking changes have at least one version of overlap** (owner, 2026-10-19T03:28:04Z: "it is a standing rule for the session: breaking changes must have *at least* one version of overlap"). A breaking change to a published API is made in at least two published versions: the first adds the new form beside the old one (both work), and a later one removes the old form once no dependent uses it. No single version may leave a dependent's newest archive unable to type-check. Every brief that touches a published package says so.

## How decisions are made

* Research before design: what comparable software does, written down where it is decided (CLAUDE.md "Decisions are made by research").
* Stop inventing threat models; trust is not a problem the project has. A cache that can be wrong is a correctness bug whoever caused the change.
* A proof is a proof: static, from types and lemmas; say "tested" when only tested. No runtime checks standing in for proofs.
* No mtimes in freshness. We write bats, not shell (quire#646). The bootstrap/c regenerate-and-compare check catches a forgotten update; it is not a security check.
* Report outcomes by their evidence: the command and what it printed. A claim is never larger than its evidence, and is never made smaller to fit it: the work is made to match the claim.
* **`Honesty is never an excuse`** (orchestrator, 2026-10-28, the owner's ruling of that date; the title is his phrase). A limitation is not admitted in a comment, a PR body or a report: it is removed. What cannot be done is escalated as not done, with what was tried and why it failed. Work is never "mostly" done or "done except": it is not done.
* **A pitboss tool that does not work is fixed, never shimmed** (orchestrator, 2026-10-28, the owner's ruling of that date). The fix is a worker in dev-skill-up/pitboss. A tool that fails is read another way (`api.github.com` through `gh api`), and the failure is not reported as unreadable.
* The owner's preferences in the system prompt apply to every message (no analogies unless they help, no "makes you wonder", search before factual claims).
